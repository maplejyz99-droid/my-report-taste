## S02 — A filter selects candidates before ranking

- role: main
- target_seconds: 45

### Script

查询先经过候选筛选，再交给排序器。筛选器选出较小的集合，排序器只对收到的候选排序，最后输出排名第一的结果。因此，筛选阶段如果漏掉了有用的候选，后面的排序就无法把它找回来。这里的图只解释概念上的执行顺序，没有证明实际节省多少计算，也没有证明候选召回率足够高。

### Transition

所以，我们需要同时比较两项指标，不能只看速度。

### Short script

筛选器选择候选，排序器再排序。被筛掉的有用候选无法由后续排序恢复，因此仅靠这张流程图不能证明收益。

## S03 — The compact setting reaches 86.0% at 85 ms

- role: main
- target_seconds: 60

### Script

表格保留了合成示例的全部设置。基线准确率为 84.0%，每次查询耗时 120 毫秒。紧凑筛选达到 86.0%，耗时 85 毫秒；相对基线，准确率提高 2.0 个百分点，耗时减少 35 毫秒。较大筛选达到 86.5%，但耗时为 160 毫秒。它是三者中准确率最高的，也是延迟最高的。这里没有任何不确定性估计，所以不能把这些人为设定的差异说成稳定提升。

### Transition

这个限制决定了我们最后能得出多强的结论。

## S05 — Metric definitions and arithmetic

- role: backup

### Answer

准确率表示排名第一的结果正确的比例。86.0% 与 84.0% 相差 2.0 个百分点，不是相对提升百分之二。延迟单位是每次查询的毫秒数，绝对减少 35 毫秒；再除以基线 120 毫秒，约为 29.2%。这些计算都只针对合成示例。
