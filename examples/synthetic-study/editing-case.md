# 同一份材料怎样变成可核对的汇报

这是手工编写的教学编辑案例，使用原有 [source.json](source.json)。它展示希望实现的编辑行为，不是代理自动运行记录，也不是有／无 skill 的收益对照。

## 原始笔记形态

> Baseline 84 / 120；Compact 86 / 85；Large 86.5 / 160。前一个数是准确率 %，后一个是 ms/query。先筛候选再排序。没有测重复性、硬件与工作负载变化、内存或候选召回。所有数值都是虚构教学数据。

## 内容组织后的结果页

研究问题：候选筛选如何改变准确率与延迟的比较？

主张：在这组教学数值中，Compact 相比 Baseline 准确率增加 2.0 个百分点，延迟减少 35 ms。

| 设置 | 准确率（%） | 延迟（ms/query） |
| --- | ---: | ---: |
| Baseline | 84.0 | 120 |
| Compact filter | 86.0 | 85 |
| Large filter | 86.5 | 160 |

同页解释：Large 相比 Compact 多 0.5 个百分点，同时多 75 ms。相对延迟减少 29.2% 的分母是 Baseline 的 120 ms，不能把 2.0 个百分点写成 2.0% 相对提升。

证据边界：没有真实实验或部署结论；未测量项保留，不补写随机种子、误差线或硬件。

如果下一条请求只是“把表格放大”，允许改变字号、位置与合理换行，不应删除 Large 那一行，不应把结论改成“Compact 普遍最优”，也不应重排其余页面。
