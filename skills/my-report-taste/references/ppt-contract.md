# 幻灯片输出契约（含 PPTX 检查）

## 目标

把 PPT 视为讲述界面，而不是缩小的长文。默认服务口头汇报；若用户明确要求“可独立阅读的幻灯片”，再提高页面自解释程度。

内容计划与版本规则也适用于 HTML／Marp 等幻灯片。备注标记、PPTX 对象和 `verify_deck_plan.py PLAN.md DECK.pptx` 仅用于真实 PPTX；其他引擎直接对照页面内容、顺序与渲染，不为验收额外生成 PPTX。报告型 PDF 和直接 Markdown 按各自契约工作。

学术论文 Oral、会议报告、论文组会或单篇论文讲解还须读取 [academic-paper-oral-workflow.md](academic-paper-oral-workflow.md)。该工作流补充论文理解、证据台账、方法分层、主讲／备份划分和移交要求，不替代本契约，也不覆盖会议官方模板或用户提供的母版。

## 内容切片

- 先确定受众、汇报目标、时间和期望决策，再确定页数。
- 每页只承担一个主要问题或结论；标题优先表达结论，不使用大量“实验结果”“分析”之类空标题。
- 把背景压缩到理解结论所需的最小范围；细节、完整参数、补充表格和引用进入附录。
- 让主张与证据同页或紧邻，避免先堆多页过程、最后才出现结论。
- 章节分隔只用于真正的叙事转折，不按固定页数机械插入。
- 多页序列保持明确进度：问题 → 证据 → 解释 → 决策或下一步。
- 每个模块必须服务于当前页的中心判断；不能说明关系的模块应删除、移入附录或拆页。
- 证据只有在最终成品尺寸下仍可读、可定位且口径完整时，才算进入主讲页；高分辨率原图或截图本身不等于可读证据。
- 页面骨架必须随定义、机制、数据、边界与决策职责变化；除有意设计的同组序列外，不连续机械复制同一种“标题 + 模块 + 总结”外壳。

## 持久化计划与立场契约

每个 PPT 版本在成品资产目录保留两份文件：`slide-plan.md` 与 `verification.md`。例如 `assets/<deck-v2>/slide-plan.md` 和 `assets/<deck-v2>/verification.md`。临时目录只用于渲染、导出和缓存；唯一页面计划不得只存在于 `/tmp` 或其他临时路径。

`slide-plan.md` 保留 `Communication job`、`Source of truth`、`Scope` 与 `Taste`，并在 YAML frontmatter 中放三个受保护字段。事实源写明文件／原文定位与版本，区分原始证据、用户确认记录和派生整理稿；旧文件无计划时可以重建“基于现状的基线”，不得称其为历史已确认意图。

```yaml
---
stance_mode: recommendation
primary_recommendation: "先核验 E1，A 保留备选"
user_decision_status: proposed
---
```

- `stance_mode` 只取 `recommendation`、`menu`、`factual`。用户要求选择、排序、建议或下一步时使用 `recommendation`；用户明确要求只列候选且不排序时使用 `menu`；论文讲解、实验结果或状态同步不要求选择时使用 `factual`。
- `primary_recommendation` 在 `recommendation` 下必须是稳定、简短且可比对的具体建议，并以相同文本出现在至少一张 `main` 页的可见正文中；只放在备注、可跳过页或附录不算主线保留。在 `menu` 与 `factual` 下写 `none`。该字段一经写入即不再润色：机器只能做规范化文本比对，迁就成品改计划等于放弃基线。确需换说法时走语义修改流程，同时更新计划与成品，不静默改锚点。
- `user_decision_status` 只取 `proposed`、`confirmed`、`not_required`。助手根据用户的推荐型任务提出初稿时可写 `proposed`；菜单模式必须能追溯到用户明确选择并写 `confirmed`；纯事实报告通常写 `not_required`。

`confirmed` 只是声明，不是授权证据。用户的明确指令、确认原话或可定位记录写进 `verification.md`；审核者必须核对来源，不能由助手自行填一个字段替代用户决定。不增加第四个必填 frontmatter 字段。

每页使用稳定 ID（如 `## S01`），记录 `role`、`title`、`claim`、`evidence` 与 `next`。`role` 只取 `main / optional / backup`；它表示讲述优先级，不等于页面职责。按需增加 `page_role`（如 method / result / boundary）与 `density_mode`；所选路线要求的字段仍须填写。字段用单行 `- key: value`，长解释放普通正文；三个表头字段和同页字段不得重复。

新生成且可写备注的 PPTX 每页只保留一组身份标记，如 `[slide-id:S01] [role:main]`。缺少标记默认按 `required` 失败；旧文件无法安全补备注才用 `--notes-policy warn` 并解释原因。`warn` 只降级缺失，角色／ID 不符或含矛盾标记仍失败。整套无标记折叠成一条警告或错误，明确检查未生效。`ignore` 仅用于显式诊断，不能据此声称身份与角色验收完成。

```markdown
## S01
- role: main
- page_role: decision
- title: 先选一种代价，做出一个扎实结论
- claim: 当前建议先核验 E1，A 保留备选。
- evidence: 推荐、备选与停止线。
- next: 与导师确认研究主线。
```

改版必须读取上一版计划并分类记录变化：

- **呈现修改**：截图、颜色、字号、裁切、对齐与不改变意义的措辞，可自主执行。
- **结构修改**：页序、拆页／合页、主讲／附录角色，必须在 `verification.md` 输出 plan diff。
- **语义修改**：`stance_mode`、`primary_recommendation`、优先级、停止条件或结论强度，必须显示旧值、新值和影响，核对用户授权。已有对应明确指令不重复询问；尚未授权的立场选择先问用户。Reviewer 的建议默认是 proposal；“这是你的判断”的分叉保持 `unresolved`，普通“继续”不构成选择。明确原始证据能证明的抄录／计算错误可按任务授权纠正并记录来源，不以保护基线为由保留已知错误；若改变研究取舍，仍需核对决定权限。

每个版本使用自己的两份文件，不覆盖旧版计划。当前版 `verification.md` 同时保存“上一版计划 vs 当前计划”和“当前计划 vs 当前成品”的比对结果。

完整新作没有上一版时，基线与版本差分标为“不适用”，不为运行差分制造旧版。待决项标明受影响页和依赖；其余已授权的呈现修改可继续，不能把一个局部待决项扩大为整项任务暂停。

脚本自动输出三个受保护字段及逐页增删、顺序、角色、标题、主张、证据、衔接和已填写的职责／密度变化；它不能判定文字变化是否等义。逐页变化产生待核对信号，不一概要求用户批准改字。不得为让检查通过而删除 `--previous-plan`、重编号隐藏删页，或反向修改旧版计划。

## 视觉与版式

- 默认使用 `16:9`，除非既有模板、会场或用户要求指定比例。
- 建立稳定网格、页边距、标题位置、页码和强调色角色；允许页面类型变化，但不得让对齐基线随机漂移。
- 正文字号以现场距离可读为准；常规正文优先约 `22–28 pt`，图注与轴标签通常不低于 `14–18 pt`。小空间不得靠无限缩字解决，应拆页、删减或移入附录。
- 一页保留一个最强视觉焦点。多个图表同时出现时必须形成比较关系，而不是并排堆积。
- 颜色负责语义角色并保持一致；不能只靠颜色区分类别或好坏。
- 动画只用于揭示顺序、状态变化或空间连续性；提供无动画仍成立的静态版本。
- 页面颜色、字体、间距、圆角、线条和阴影优先由设计 token 统一管理，不在每页临时发明数值。

## 中英文字体与可移植性

- 中文为主、英文缩写与数字较多的高保真默认候选：中文使用 `Source Han Sans CN`，英文/数字/单位使用 `Source Sans 3`。两者都有完整字重和开放许可，字面率接近，适合技术、经营与数据页。
- 编辑型高密度材料可用 `Source Han Serif CN` 做大标题或引语，正文、表格和图表仍回到 `Source Han Sans CN`；不得整份报告无差别使用宋体。
- 跨机器编辑优先的安全回退：中文 `Microsoft YaHei`，英文/数字 `Arial`。安全回退属于交付策略，不应与高保真字体在同一页随机混用。
- 字体角色、字重、字号、行距和中英混排规则见 `TYP-002`。必须先确认目标机器是否安装所需字体；PPTX 未嵌入字体时，跨机观看优先交付已验收 PDF。
- 禁止依赖编辑器界面中的正常预览判断字体安全；无头导出、不同 Office 实现和临时用户配置可能触发替换。

## 表现层与生成引擎

- `my-report-taste` 决定选什么视觉语言；PPTX、HTML deck、Marp、SVG 或视频工具决定怎样实现。不得把某个生成引擎自带的主题误当成用户偏好。
- 需要原生编辑、批注、企业模板兼容时优先 PPTX；需要连续镜头、路径绘制、复杂对象编排或网页交互时优先 HTML deck，并按需附 MP4；只做独立阅读时优先 PDF 的静态终态。
- 同一设计系统可以跨媒介复用，但必须分别适配：PDF 不保留交互假设，PPTX 不承诺网页级连续镜头，HTML deck 不假装具备原生 PowerPoint 对象编辑能力。
- 任何动效交付至少包含一个可复现源文件和一个稳定观看版本；外部字体、CDN、地图瓦片或脚本失效时，关键内容仍可见。

## 动效设计

- 每页先记录一个 `motion_form`；默认 `motion:none`。复杂页最多一个主配方和一个辅助配方，避免把效果目录当作必选清单。
- 封面 / 收尾：可用 `motion:camera-zoom` 或拼贴镜头，建立“整套 → 单页 → 整套”的空间连续性。
- KPI / 关键结论：用错峰上升、数字递增或单焦点放大；卡片终态必须同时可比较。
- 图表：坐标与预算线先出现，数据路径从左到右绘制，关键节点和注释最后进入；禁止用动画掩盖不准确的数据映射。
- 流程 / 系统：按真实方向依次点亮节点、边和结果；中心—外围结构可用 `motion:orbit-expand`，但展开后关系线与标签必须稳定。
- 对比页：左右方向或前后状态应与逻辑对应，不使用随机飞入。
- 常规对象入场以约 `180–700 ms` 为主；连续镜头可以更长，但同一页不应让所有对象无限循环。
- HTML deck 应尊重 `prefers-reduced-motion`；重型背景或 Canvas/WebGL 效果应有静态/低功耗模式。

## 验证

1. 制作前运行 `python3 scripts/verify_deck_plan.py PLAN.md`；改版加 `--previous-plan PREVIOUS_PLAN.md`。这是计划结构预检，不是成品检查。先读标题链、主张／证据和逐页 diff，确定内容取舍；用户已授权制作且不存在待决分叉时可继续，不要求每页再获一次批准。
2. PPTX 制作后运行 `python3 scripts/verify_deck_plan.py PLAN.md DECK.pptx`，改版仍传 `--previous-plan`。默认备注检查为 `required`。页数、标题文本、稳定 ID、角色或推荐落点不一致先修复；HTML／Marp 做对应页面比对。完整输出写入 `verification.md`，包括用户决定来源与差异处理，不用总分放行。
3. 内容比对通过后，按 `qa-rubric.md` 的影响范围渲染并检查：完整新作覆盖全部页面，局部修改覆盖受影响页并核对共享母版、字体、页序等连带变化。其余页可引用上一已验收版本的证据；缺少可靠旧证据时，补足实际交付所需检查。文本存在不能证明内容未遮挡、未移出画布或可读。`check_coverage` 中未执行的检查据实保留，plan-only PASS 不得写成成品 PASS。
4. 检查文字、图表、图片、页码和注释是否越界、遮挡、截断或过小。
5. 以缩略图总览检查章节节奏、留白、视觉焦点和重复页面骨架；重复对象数量只是诊断，不等于版式相同。可有意重复实验比较序列，不为追求变化破坏比较；机械套壳则回到内容计划重构。
6. 检查标题是否能独立构成汇报摘要；相邻标题不应只是章节名重复。
7. 检查字体替换、图片清晰度、公式、图例、对比度和导出 PDF 后的差异。
8. 若存在演讲备注，确认备注没有承载听众必须看到的关键事实。
9. 若交付 PDF 派生版，运行字体安全导出流程，并检查所有字体已嵌入/子集化、Unicode 映射可用、中文文本可提取；随后逐页渲染检查字形与换行。

## 交付说明

先提供实际成品及影响使用的依赖／限制。比例、页数、时长、收藏映射、字体、动画和验证详情记录在 `verification.md`，用户要求时展开，不在交付消息中重复整份验收清单。
